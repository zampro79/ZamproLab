# Program Execution API

These endpoints are available only with `ZAM_EXPERIMENTAL_LUA=ON` and an initialized Program Manager. Lua is enabled by default; the OFF build does not register them. HTTP has no authentication or TLS: use a trusted network, do not expose it directly to the Internet, and do not treat Lua as a complete sandbox.

`POST /api/program/run` accepts `Content-Type: application/json` and exactly two string fields: `path`, a valid logical UserFS path of at most 192 characters, and `request_id`, a lowercase UUID `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`. The body is limited to 512 bytes; extra or duplicate fields, Unicode escape sequences, NUL and malformed JSON are rejected. HTTP 202 means queued, not successful execution. A missing source can later yield `load_error`.

```sh
curl -H 'Content-Type: application/json' -d '{"path":"/projects/hello.lua","request_id":"f8b7c91e-62a4-4d90-8f35-1b2c3d4e5f60"}' http://DEVICE/api/program/run
curl -X POST http://DEVICE/api/program/stop
curl http://DEVICE/api/program/status
```

RUN and STOP return `{"accepted":true,"state":"..."}` with the state observed after the operation. STOP on IDLE is idempotent and returns 200; while STARTING, RUNNING or STOPPING it requests cooperative stop and returns 202 without waiting for cleanup. A nonempty body is rejected and CLEANUP may return 409. Only one execution is admitted. The volatile idempotency registry retains up to 64 request identifiers for 120 seconds; repeated requests with the same ID and path are deduplicated, and reuse with a different path conflicts. The registry is not persistent across reboot. A duplicate accepted ID with the same path returns 202 and `{"accepted":true,"duplicate":true}`; a pending request returns 409 `request_pending`, and the same ID with another path returns 409 `request_id_conflict`. When all 64 entries are occupied, new RUN requests return 503 `request_registry_full`; valid entries are not evicted early. The guarantee does not extend beyond expiry or reboot, and a delayed STOP can theoretically affect a later run.

`GET /api/program/status` returns `state` (`idle`, `starting`, `running`, `stopping`, `cleanup`), `last_result` (`null`, `ok`, `stopped`, `syntax_error`, `runtime_error`, `memory_error`, `load_error`, `internal_error`), `last_memory` (`live`, `peak`, `limit`, `stack_free`), `output` (`produced`, `dropped`) and `last_timing_us` (`load`, `run`, `cleanup`, `stop`). Last metrics describe the last completed run, not the active VM. The current path is not exposed. See [Terminal](terminal-http.md) for output polling and [output design](output-stream-design.md) for loss semantics.

Errors use `{"error":{"code":"...","message":"..."}}`: 400 invalid input, 408 body timeout, 409 conflict, 413 oversized body, 415 media type, 500 internal error, 503 unavailable. A 405 includes `Allow`. Rejected bodies up to 4,096 bytes receive bounded draining; larger or incomplete bodies may cause connection closure instead of JSON. The 2 s body budget is checked between receives; a blocking receive can still reach the ESP-IDF socket timeout. Another client can request STOP after the initiating client disconnects.

The LAB requires a saved UserFS `.lua` file and conditional ETag save. It does not automatically retry an ambiguous RUN or STOP. Samples must be copied from WebFS to UserFS before execution. Historical phase 8A restoration instructions below refer to the Lua-OFF factory used then, not the later stable Lua-ON configuration.

## Validazione fase 8A

Sul dispositivo ESP32 Classic D0WDQ6 revisione 1.0, con ESP-IDF 5.5.3 e Lua 5.5.1, la build Lua OFF ha restituito 404 per tutti e tre gli endpoint. La build Lua ON ha superato 100 cicli misti, inclusi 20 errori di sintassi, 20 errori runtime e 10 OOM; ogni due cicli è stato avviato un loop infinito e fermato via HTTP, per 50 STOP e 100 richieste diagnostiche durante attività Lua. STATUS è stato letto oltre 100 volte; dopo ogni ciclo sono stati controllati IDLE, risultato atteso e `last_memory.live=0`. Nessun reset o watchdog è stato rilevato nella sessione completata. `zam.sleep()`, output continuo, recupero, doppia RUN concorrente (una 202 e una 409), doppio STOP e disconnessione del client seguita da STOP esterno sono riusciti. Il server ESP-IDF può serializzare gli handler: le prove HTTP non dimostrano simultaneità di esecuzione degli handler. I test host forzano anche STARTING e STOPPING, senza pretendere che le finestre brevissime siano state isolate deterministicamente via rete.

Nella campagna finale: RUN 164 richieste, mediana 49,83 ms e massimo 478,32 ms; STOP 56, mediana 41,96 ms e massimo 484,45 ms; STATUS 228, mediana 41,75 ms e massimo 1.076,19 ms. Health: 51 richieste, mediana 35,87 ms e massimo 1.878,42 ms; memory: 51, mediana 37,00 ms e massimo 259,53 ms. In una campagna precedente una singola health ha richiesto 5.380,6 ms; una serie separata di 100 health/memory durante un loop ha avuto mediana 38,03 ms, massimo 83,84 ms e zero errori. Una richiesta STATUS si è chiusa con reset TCP durante una campagna precedente e un campionatore concorrente; non si è riprodotta in 400 STATUS concorrenti né nella campagna finale. La causa della singola interruzione e dell'outlier non è determinata.

Nella sessione finale l'heap interno era 168.812 B prima, 156.128 B durante e 167.172 B dopo la campagna; minimo storico 107.072 B, blocco massimo contiguo 110.592 B. L'ultima prova flood ha riportato picco Lua 33.164 B, `live=0`, watermark stack 9.048 B, 644.525 byte prodotti e 642.477 scartati. Le condizioni e l'attività dei servizi differiscono dalla 7B.1 (baseline 163.740 B), quindi non si attribuisce una differenza isolata a leak o miglioramenti.

Test host: parsing, input vuoto/eccessivo, Content-Type, campi mancanti/duplicati/extra, percorsi invalidi, NUL ed escape, letture brevi, timeout prima e dopo ricezione, mapping di tutti i risultati, indisponibilità, RUN concorrenti e STOP; inoltre Program Manager, allocatore, Lua Core, percorsi, Wi-Fi e storage. Sul dispositivo sono stati verificati 400, 405, 413, 415, STOP IDLE 200 e body lento 408. Un primo test aveva rilevato reset TCP per il body eccessivo non letto; la lettura di scarto limitata ha corretto il caso riprodotto. Il controllo della scadenza dopo l'ultima ricezione è stato aggiunto dopo aver riprodotto un body lento accettato oltre il budget.

Le quattro build sono riuscite senza warning del compilatore rilevati: ESP32 Lua OFF 904.032 B, Lua ON 1.044.848 B; ESP32-S3 Lua OFF 901.296 B, Lua ON 1.039.888 B. Le tabelle partizioni binarie coincidono con 7C. I simboli dei nuovi endpoint e del Program Manager sono assenti nelle build OFF e presenti in quelle ON. Hardware S3 non disponibile; la configurazione S3 resta a 4 MB senza PSRAM.

Dopo i test la factory stabile Lua OFF è stata ripristinata e riletta: SHA-256 `d2eeeaee3d4b74067cc049ee86a4c1621bfdfac1f23bdb8dfde77cccd15db29d` su `0x10000–0x10ffff`. WebFS coincide con il backup; il file UserFS preesistente accessibile coincide per contenuto e i file di prova sono stati rimossi. Le impostazioni NVS controllate, i mount, la console, Wi-Fi AP+STA e le API esistenti rispondono. UserFS è stata confrontata logicamente e non byte per byte; non è stato calcolato un hash dell'intera NVS.

## Pannello LAB (fase 8B)

Il pannello esegue il file `.lua` aperto nell’editor dopo il salvataggio condizionale ETag; un conflitto 412 o un salvataggio annullato impedisce RUN. STATUS è autorevole: il risultato è globale e non viene attribuito al file attualmente selezionato. RUN e STOP non vengono ripetuti automaticamente dopo risposte ambigue. Il percorso corrente non è esposto; il terminale legge l’output incrementale tramite HTTP. Vedere [web-ui.md](web-ui.md) per polling e validazione.

## Idempotenza RUN (fase 8B.1)

Ogni intenzione RUN richiede un `request_id` nuovo. Il LAB usa `crypto.randomUUID()` oppure, su HTTP locale, UUID v4 ottenuto da `crypto.getRandomValues()`; se non è disponibile una sorgente crittografica non invia RUN. L'identificatore non è una credenziale. Non sono accettati body senza ID, campi extra o ID non conformi.

Un registro statico in RAM conserva fino a 64 identificatori, ciascuno con percorso ed esito di accettazione. La riserva avviene prima di chiamare il Program Manager ed è sincronizzata; non si mantiene il lock durante l'accettazione o la rete. L'esito, anche negativo, resta registrato per 120 secondi dal completamento dell'accettazione. Un duplicato accettato con stesso percorso restituisce 202 e `{"accepted":true,"duplicate":true}` senza avviare nulla; durante la riserva riceve 409 `request_pending`. Lo stesso ID con percorso diverso riceve 409 `request_id_conflict`. I duplicati degli errori ripetono l'esito; un nuovo ID con runtime occupato riceve 409. Se i 64 posti sono occupati da registrazioni non scadute, i nuovi RUN sono rifiutati con 503 `request_registry_full`: nessuna voce valida viene espulsa anticipatamente. La capacità consente 64 intenzioni nei due minuti, non un numero illimitato.

La garanzia vale solo nella finestra dichiarata e durante lo stesso avvio del dispositivo; il registro viene perso al riavvio. Non è una garanzia exactly-once attraverso riavvii o oltre scadenza. Dopo una risposta persa il LAB non ripete RUN e recupera lo stato globale via STATUS, che non consente di attribuire con certezza il risultato a una richiesta. STOP resta invariato: uno STOP ritardato può teoricamente interessare un'esecuzione successiva.

Test host deterministici coprono duplicati prima e dopo IDLE, conflitti, riserva in corso, concorrenza, saturazione, scadenza, errori e riavvio simulato. Su ESP32 Classic dieci duplicati dopo IDLE e cinque POST paralleli sono stati provati; per lo script breve un incremento di quattro byte nel contatore output ha verificato una sola esecuzione, oltre alle risposte HTTP. Un client ha inoltre chiuso la connessione dopo l’invio del body: un successivo duplicato non ha generato altro output; due ID distinti concorrenti hanno prodotto una accettazione e un conflitto. Registro compilato: 15.872 byte statici.

Nella Fase 9E il registro è rimasto invariato: la risposta 503 a saturazione resta prevista. La campagna hardware finale ha rispettato la finestra di 64 intenzioni/120 s e ha verificato deduplicazione e RUN/STOP concorrenti; vedere [lua-runtime.md](lua-runtime.md).
