# Version and build traceability

`VERSION` is the sole project version source. CMake passes it as ESP-IDF `PROJECT_VER`; ESP-IDF stores it in `esp_app_desc`, and the existing `/api/system` and console read that descriptor. Lua and the Program Manager are unchanged.

Build with ESP-IDF 5.5.3 and verified local dependencies. With `IDF_PATH`, `LUA_DIR`, toolchain and ESP-ROM paths configured, run:

```sh
python3 tools/package_build.py --target esp32 --lua ON --build-dir /absolute/new/build-dir --output /absolute/new/package-dir
```

Supported targets are `esp32` and `esp32s3`; Lua `ON` is the principal configuration and `OFF` is diagnostic. Both directories must be new and separate. The packager builds firmware and storage images, checks the `esp_app_desc` version, copies bootloader, partition table, factory application and WebFS, verifies SHA-256 after copying, and finally generates `release-manifest.json`. NVS is not copied; a newly generated empty UserFS is included exclusively for explicitly authorized initial provisioning. A failed build or validation does not produce a valid manifest; inspect and preserve any partial output before retrying.

The manifest identifies version, full Git commit, dirty status, a SHA-256 snapshot of tracked and non-ignored untracked files, target, Lua setting, IDF, flash, PSRAM, partition table hash, and each image's name, byte count, offset and SHA-256. The state is measured before and after the build. Ignored dependency caches and the toolchain are not included in the Git source snapshot: the packager verifies 61 Lua files when enabled and checks LittleFS files against its local checksum manifest, recording dependency fingerprints before and after. A local checksum file is not independent proof of upstream authenticity; ESP-IDF, toolchain and upstream component integrity still require independent verification. Dirty means any tracked or non-ignored untracked change, including local reports; it does not claim that every dirty file affects the binary. Never treat a dirty build as the clean commit.

Firmware version is visible through the existing diagnostic API; no extra browser polling is added. WebFS is associated with the same source state and version by the package manifest, not an embedded endpoint. Hashes bind the actual images. Compare the version and artifact hashes against the manifest to identify a pair; matching version or commit alone is insufficient to establish binary identity. Different commits do not necessarily imply functional incompatibility. A WebFS-only update or factory restore can produce a mixed pair: retain both manifests and assess compatibility; the firmware does not automatically negotiate it.

Build reproducibility depends on tool versions, paths and timestamps; compare independent build artifacts and report actual results. The generic S3 configuration uses 4 MB. The packager supports Classic 4 MB, generic S3 4 MB, verified S3 RGB 16 MB without PSRAM, and the explicitly selected `s3-rgb-psram-16mb` profile for the verified N16R8 board; generated packages are private evaluation artifacts, not official releases. No tag, release, device flash, NVS or UserFS backup is part of this process. MIT is approved for original project material and Spleen replaces the previous font; final third-party inventory and notices remain open. See the [distribution proposal](distribution-proposal.md).

The phase 14D comparison and exact build hashes are recorded in [release-readiness.md](release-readiness.md). The firmware does not embed the full Git commit or dirty flag; that information is in the external manifest, so the manifest must remain paired with the verified binary. A copied image alone cannot establish its source commit. `SOURCE_DATE_EPOCH` may be set by the build operator; record it separately when comparing builds.

Phase 14D.1 hardens packaging: build and output must be new directories outside the repository; the selected target and Lua setting are checked against build metadata, the app descriptor's ELF hash against the built ELF, and factory/WebFS offsets against the generated partition entries. Paths, duplicate names, empty/missing images, sizes and copied hashes are checked before the manifest is atomically published. Git status conservatively includes every non-ignored untracked file, including unrelated local licensing reports; this is documented and may label an otherwise identical input tree dirty. Ignored SDK/toolchain inputs are outside the Git snapshot and their upstream authenticity is not proven by local checksums.

Negative tests in `tests/test_package_negative.py` exercise missing/empty files, wrong path/offset, wrong partition entries, duplicate names, swapped source, symlink, unreadable and unwritable errors (the latter simulated), malformed/missing version, invalid target/Lua, incompatible flash/Lua configuration, mixed app/ELF and incomplete manifest. These are controlled fixtures and are not an exhaustive filesystem or adversarial attack audit. The current validation checks required partition entries and image markers, not the partition table's embedded MD5 or an independent full verification of ESP-image checksum. Never present this as complete validation of arbitrary untrusted binaries; packaging uses freshly generated build outputs.


For the experimental N16R8 PSRAM package, use `--target esp32s3 --lua ON --profile s3-rgb-psram-16mb`. It requires a board with 16 MiB flash, 8 MiB octal PSRAM and the verified GPIO48 GRB LED; configuration checks cannot identify physical hardware. Resolved configuration must enable octal PSRAM at 80 MHz, memory test, the PSRAM-only Lua allocator and the 262,144-byte limit. The manifest adds `psram_configuration`, `lua_heap_limit` and `lua_allocator` only for this profile; existing manifest fields and older profiles remain supported. The empty UserFS is newly generated, never copied from a device, and is for an expressly authorized initial installation only. Follow `FLASHING.txt`, verify the layout and back up existing data before writing; update instructions omit UserFS.

Package ZIP timestamps and file modes are normalized for reproducible archiving of the same package files under the same top-level directory name. This does not establish bit-for-bit reproducible independent firmware builds. The profile is experimental and the generated package is not an official release.
