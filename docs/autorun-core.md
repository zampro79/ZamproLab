# Autorun at boot

The Program Manager runs an Autorun sequence at each boot using its existing worker, after UserFS and WebFS are mounted, console, Wi-Fi and Program Manager are initialized, and HTTP has started. This is a readiness check, not proof that a client can connect. A missing or failing required service skips the sequence; no automatic retry occurs. No persistent setting, recovery mechanism or public endpoint to start a sequence is provided.

**Boot-loop limitation:** state is held only in RAM. After reset the directory is scanned from the beginning and every eligible script runs again. A script that repeatedly resets or blocks the board can make browser recovery unavailable. This version has no guaranteed independent recovery; do not rely on it where an inaccessible device would be unacceptable. STOP is cooperative and may be delayed by native calls.

A request owns the executor until it reaches COMPLETED, CANCELLED or FAILED. Manual RUN is busy throughout scanning, execution and cleanup. STOP cancels the entire sequence and is cooperative while Lua or native operations are active. No second Lua task or persistent interpreter is used. Each file uses the existing runtime, with a new Lua state, existing memory cap and cleanup. The output ring is reset per script as for ordinary RUN; sequence status records the last script and result, not an output archive.

`/autorun` is a UserFS path. A missing or empty directory succeeds with no scripts and is not created. Inventory is limited to 32 regular `.lua` files and 256 total entries; a name is limited to 63 bytes. Excessive or invalid names, I/O failure and overflow fail the sequence before executing any file. Directory entries reported as non-regular, including directories, are ignored. Sorting uses bytewise `strcmp`, so ASCII uppercase precedes lowercase; `.lua` is case-sensitive. Storage reserves 2,048 static bytes for names, plus fixed status and worker stack.

The initial inventory freezes names, not contents. Each source is copied by the runtime when its turn begins under the existing short UserFS lock, then executed after release. Edits before that snapshot change what runs; new files wait for the next request; an unreadable or removed file fails the remaining sequence. The scan holds the existing file lock while traversing its bounded directory. The underlying LittleFS VFS presents only regular file/directory types and does not implement symbolic links; the scanner skips non-regular entry types and fails if the type is unknown. The implementation assumes the LittleFS VFS behavior described above; checks on specific hardware do not establish behavior for other filesystems.

The internal API is `zam_program_autorun_start`, `zam_program_autorun_cancel`, `zam_program_autorun_status` and `zam_program_autorun_busy`; existing `zam_program_stop` cancels an active sequence too. A failed script stops the sequence and records its basename, result enum and a short generic diagnostic. STOP during scanning, between scripts or cleanup prevents the next script. The existing `GET /api/program/status` adds an `autorun` object with state, current basename, counts, result and message. No persistent recovery latch exists. The LAB Execution panel provides the file-management actions described below; it does not add a Settings toggle.


## Managing Autorun from LAB

Open a saved UserFS `.lua` file in the editor. **Copy to Autorun** copies it to `/autorun/<basename>` for the next boot. Creating a new copy does not require a confirmation dialog; replacing an existing destination does. Copy uses an atomic destination precondition (`If-None-Match: *` for creation, `If-Match` with the destination ETag for replacement); it reads a stable source snapshot and verifies the destination after the operation. Unsaved editor changes must be resolved first. Copying an existing `/autorun` file into the same directory is not offered.

**Remove from Autorun** asks for confirmation and removes the matching destination with `If-Match`; it verifies absence afterwards. The backend rejects protected mutations during an active sequence. A 409 can indicate active Autorun, busy storage or a directory limit; a 412 indicates a stale precondition. A lost response can leave the outcome unconfirmed: inspect the directory before retrying. Other file operations have their own concurrency rules; do not assume every DELETE is atomically conditional.

Neither copy nor remove runs a script immediately. After each reboot the directory is scanned anew, with no persistent enable flag or recovery latch. A problematic script may make the device inaccessible; STOP is cooperative and cannot guarantee interruption of a blocking native call.
