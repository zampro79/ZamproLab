# LAB / SYSTEM Web UI

LAB provides the Explorer, a UserFS File Manager and text editor, an Execution panel and an output Terminal. SYSTEM displays diagnostics from `/api/health`, `/api/system`, `/api/memory` and `/api/wifi/status`. Storage capacity is not available through a dedicated HTTP API. SYSTEM → Settings provides Wi-Fi station configuration and explicit scans; see [Web Settings](wifi-web-settings.md). Other device configuration remains available through the serial console.

Open or create a UserFS text file, edit and save it with its ETag, then request RUN. STOP is cooperative. STATUS is authoritative and represents the global Program Manager, not necessarily the selected file. The Terminal uses HTTP polling and reports lost output; it does not provide interactive input or WebSocket. See [Program API](program-api.md) and [Terminal](terminal-http.md).

Open Samples in Explorer, inspect a read-only example, choose **Copy** to copy it into the current UserFS directory, open and save the copy, then use RUN and STOP. Samples cannot run directly from WebFS. Peripheral-specific BME280 and SSD1306 libraries and dependent Samples are not included. Existing names use an ETag-protected replacement confirmation.

The Execution panel offers **Copy to Autorun** and **Remove from Autorun** for saved Lua files, with confirmations and conditional destination checks. See [Autorun at boot](autorun-core.md) for sequencing, STOP, boot-loop and recovery limitations.

The File Manager lists and navigates directories and supports creation, rename, deletion, download and sequential uploads of up to 512 KiB per file. Replacement requires confirmation. Binary or invalid UTF-8 files remain downloadable but are not opened in the text editor. Unsaved edits trigger a warning; browser behavior determines the unload warning. ETag conflicts preserve the text; legacy unconditional PUT clients can still overwrite files. ZIP is unavailable.

The desktop LAB has resizable Explorer and Terminal panes; mobile uses panel navigation. At 1051 px and wider, Explorer width and Terminal height can be changed with pointer or keyboard; Home/End select limits, double-click or Enter restores defaults. Layout preferences are stored in localStorage when available. Theme selection is stored in the browser. See [File Manager](files.md) for path restrictions, concurrency and ETag behavior. HTTP has neither authentication nor TLS: use a trusted local network and do not expose the LAB to the Internet.

## Build and recovery

`web/index.html`, `web/style.css`, `web/app.js`, `web/terminal.js` and `web/highlight.js` are sources. `tools/bundle_samples.py` embeds Samples and libraries in generated JavaScript, and `tools/build_storage_images.sh` creates and verifies WebFS. Each generated asset must fit the 64 KiB streaming limit. A WebFS with assets larger than 16 KiB requires a matching streaming-capable Factory; never install it alone on older firmware. See [storage](storage.md) for image generation, partition offsets, backup and explicit provisioning. Application-only flash does not install WebFS. Never overwrite UserFS or NVS data to preserve; do not use `erase-flash`.

The diagnostic dashboard refreshes every five seconds after a cycle completes; requests use timeouts and polling pauses while the page is hidden. On errors, stale values remain marked as such. Execution polls every 500 ms while active, 5 s when idle and 30 s after a 404, without overlapping polls. Changing views or reconnecting resynchronizes state. The theme and desktop splitter proportions are stored only in browser localStorage when available; the defaults are 25% Explorer width and 30% Terminal height.

## Verifiche Fase 5

Su ESP32-D0WDQ6 rev. 1.0, dopo il flash del solo firmware e di WebFS, entrambi i filesystem risultano montati e la STA si riconnette con la configurazione conservata. Le risorse occupano 15.633 byte (HTML 5.450, CSS 5.121, JavaScript 5.062); l'immagine è 786.432 byte e WebFS riporta 32.768 byte usati. Il backup precedente di WebFS e dell'intera factory è stato letto due volte e verificato; un ripristino effettivo non è stato eseguito. La versione precedente di WebFS può essere ripristinata da sola, mantenendo il nuovo firmware; questa combinazione non è stata provata sulla scheda.

Con Firefox 157 headless sulla rete STA sono state verificate cinque dimensioni da 1920×1080 a 390×844, 20 cicli LAB/SYSTEM, 20 cambi tema, 10 ricaricamenti e persistenza del tema. Un controllo automatico non sostituisce la verifica visiva completa. Sono riuscite 105 richieste HTTP distribuite tra risorse e API; i percorsi di traversal provati rispondono 404. L'heap libero misurato via API durante le prove è passato da 188.720 a 187.880 byte, con minimo 165.404 e blocco interno massimo 110.592 byte; le misure sono influenzate dall'attività Wi-Fi e dal browser. Il test diretto tramite AP e la prova fisica di disconnessione e riconnessione non sono stati eseguiti.

Su server locale di prova, Firefox ha inoltre verificato il ripiego su Auto con `localStorage` bloccato e la conservazione dei dati segnalati come non aggiornati durante una disconnessione simulata, seguita dal ritorno a Online. Timeout, errori HTTP, cambio del tema del sistema operativo e controllo visivo completo non sono stati verificati separatamente.

## Verifiche Fase 6B

Su ESP32-D0WDQ6 con Firefox 157 headless sono stati verificati 20 aperture e salvataggi, testo UTF-8 multilinea, conflitto tra versioni con conservazione del testo locale, upload binario e rifiuto dell'apertura nell'editor, rinomina, eliminazione, 20 cambi LAB/SYSTEM e 10 ricaricamenti. Le cinque risoluzioni da 1920×1080 a 390×844 non mostravano scrolling orizzontale nel controllo automatico. Il confronto binario del download è stato effettuato tramite API, non con il selettore di salvataggio del browser. Un test automatico ha atteso troppo poco la fine del caricamento dell'editor ed è stato corretto e ripetuto.

Il server con sette socket e senza espulsione LRU si è saturato con sessioni browser di prova rimaste aperte; la configurazione ora abilita l'espulsione della connessione meno recente. Nove client HTTP persistenti sono stati serviti in successione nel test. LRU può chiudere una connessione inattiva quando ne arriva una nuova; i client devono gestire eventuali riconnessioni.

La Fase 6B richiede il firmware che supporta ETag e scritture condizionali; ripristinare il firmware precedente lasciando la nuova WebFS non fornisce tali garanzie. Prima dell'installazione sulla scheda di test sono state verificate due letture di WebFS (`0x210000`, `0xC0000`) e della regione firmware precedente (`0x10000`, `0xE0000`, che copre interamente il binario installato). Per un rollback completo usare entrambe le copie ai rispettivi offset, senza scrivere NVS o UserFS; il ripristino effettivo non è stato eseguito.

Con la versione installata, HTML occupa 5.872 byte, CSS 6.469 e JavaScript 14.736, per 27.077 byte complessivi. L'immagine WebFS è 786.432 byte e il filesystem riporta 40.960 byte utilizzati. Sono stati verificati cinque riavvii con persistenza di un file di prova; dopo la pulizia dei soli file di test, UserFS riporta 8.192 byte usati. Il test non copre upload multipli, il dialogo di download del browser, spazio esaurito, interruzione fisica della rete o hardware ESP32-S3. L'API HTTP binaria è stata verificata byte per byte; la prova responsive automatica non sostituisce una revisione visiva completa.

### Verifica su ESP32 Classic

Su ESP32-D0WDQ6 rev. 1.0 sono stati provati Firefox headless, Lua ON e la nuova WebFS: salvataggio, conflitto ETag, script breve, errori sintattici e runtime, OOM con recupero, STOP di `zam.sleep()`, ricaricamento durante esecuzione e 50 cicli RUN/STOP con 120 letture STATUS. Nessun reset, watchdog o output Lua su UART è stato rilevato nella sessione completata. Health durante il ciclo: mediana 76,44 ms, massimo 250,76 ms; heap interno libero finale 160.304 B, minimo storico 110.864 B. Sono misure puntuali, non una prova di assenza di perdite. Tre dimensioni da 1366×768 a 390×844 e temi Auto/Light/Dark sono stati controllati automaticamente, senza sostituire un controllo visivo completo. Con firmware Lua OFF la nuova WebFS segnala l’assenza del runtime e mantiene editor e File Manager operativi.

Dopo le prove sono stati rimossi i soli file temporanei, ripristinati firmware stabile Lua OFF e WebFS precedenti e riletti i rispettivi backup. Console, Wi-Fi AP+STA, mount e servizi HTTP funzionano; il file UserFS preesistente accessibile coincide con il backup e le impostazioni NVS controllate sono conservate. Il confronto UserFS è logico, non byte per byte, e non è stato calcolato un hash completo di NVS. Hardware ESP32-S3 non disponibile; nessun flash S3. Non è stato verificato il salvataggio fisico del download tramite il dialogo del browser.

### Analisi della disconnessione e fase 8B.1

Il test 8B aveva osservato dieci POST dopo una sola intenzione, ma la causa non era stata isolata. Una riproduzione isolata ha registrato una sola POST, ma il test frontend strumentato ha riprodotto il caso intermittente: una chiamata JavaScript `fetch`, dieci POST complete su dieci connessioni TCP distinte, con stesso percorso, body e identificatore, e un solo avvio nel server simulato. Il server chiude la connessione dopo aver letto l’intero body e prima di rispondere. Si tratta di richieste HTTP distinte, non segmenti duplicati dello stesso flusso TCP; non si è osservato retry nel codice applicativo. Altre ripetizioni hanno prodotto una sola POST. La deduplicazione server protegge anche i duplicati inviati da altri client: dettagli, capacità e limiti in [program-api.md](program-api.md).

Con la build Lua ON aggiornata, la verifica browser su ESP32 Classic ha ripetuto 50 RUN/STOP e 114 STATUS, scenari ETag, errori Lua, OOM, sleep, ricaricamento e temi responsive. Health durante la serie: mediana 60,81 ms, massimo 200,28 ms; heap interno libero 150.696 B e minimo storico 93.100 B. Le misure dipendono dal carico e non dimostrano assenza di perdite. Il watermark stack finale dello script era 9.048 B e la memoria Lua live dopo cleanup zero. Dopo i test factory Lua OFF e WebFS precedenti sono ripristinate, con verifica indipendente; UserFS è confrontata logicamente e NVS tramite le impostazioni accessibili.

Nella Fase 9E il programma di esempio in `/projects/zamprolab_hello.lua` è stato salvato ed eseguito dal LAB, con output progressivo, STOP e successivo RUN. L'accesso AP è stato confermato dall'utente con un secondo dispositivo; la verifica automatizzata Firefox è stata eseguita via STA. Vedere [lua-runtime.md](lua-runtime.md) per misure e limiti.

## Historical validation: phase 9F

La verifica Firefox della Fase 9F copre trascinamento e annullamento, limiti, tastiera, reset, preferenze valide e non disponibili, ricarica, temi, copia del testo, output durante il resize e viewport mobile simulata. Su ESP32 Classic con firmware Lua ON è stato modificato e salvato un file di prova dedicato, quindi eseguito, ridimensionato il terminale durante l'output, fermato e rieseguito. La WebFS è stata riletta dopo la scrittura; factory, NVS e tabella partizioni corrispondevano byte per byte ai rispettivi backup e i file UserFS preesistenti sono stati verificati per contenuto.

The editor displays one-based line numbers and a status bar with the caret's one-based line and column. The gutter follows vertical scrolling; long lines scroll horizontally without wrapping. For a backward selection it uses the active start; otherwise it uses the selection end. Columns count textarea UTF-16 code units, so a tab counts as one and characters represented by a surrogate pair count as two. Textarea line endings are normalized by the browser. Line numbers and position were checked on the ESP32-S3 LAB with Firefox and visually over AP; mobile layout was simulated rather than validated across physical mobile browsers.
